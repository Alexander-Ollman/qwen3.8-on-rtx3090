Field notes · 2× RTX 3090 · August 2026

27 to 212 tokens a second

Five days tuning one 27B model on consumer hardware. The model never changed. The serving software made it 7.7× faster — and along the way, four different things quietly lied to us about how fast it was going.

We had two RTX 3090s and Qwen3.8-27B, a 27-billion-parameter hybrid-attention model, quantized to 4 bits. The question was simple: how fast can this actually go on hardware you can buy secondhand?

The out-of-the-box answer was 27.6 tokens per second. Install llama.cpp, point it at the model, pass one flag to put the layers on the GPU. It works, and it is slow enough to be annoying.

Five days later the same model on the same card was doing 212.1. We had not quantized it further, swapped it for something smaller, or overclocked anything. Every one of those tokens came from the same 4-bit checkpoint.

What follows is how we got up that ladder, and — more usefully — the four times we thought we had a result and didn't.

Day one: we killed a GPU

The first real measurement run ended with a card falling off the PCIe bus. nvidia-smi reported Xid 79 and then stopped reporting the GPU at all. A reset didn't help. Only a reboot brought it back.

The obvious suspect was the software that had been running — a kernel autotuner hammering the card. The actual cause was electrical. Xid 79 on an RTX 3090 is the signature of a 12 V rail brownout: the autotuner had been cycling the GPU between idle and full power hundreds of times in a few minutes, and the power supply couldn't track the transients.

sudo nvidia-smi -pl 250    # cap each GPU at 250 W
sudo nvidia-smi -pm 1      # persistence mode
This is the first thing to do on a multi-3090 box. We later proved the diagnosis by deliberately re-running the exact workload that killed the card, after capping. Eight server starts, no recurrence. The cap costs about 14% on unassisted decode and nothing measurable on the optimized path — cheap insurance against a hard lockup mid-run.

The lever that actually matters

Almost everything people tune — batch sizes, cache dtypes, thread counts — is worth single-digit percentages. One thing is worth double: speculative decoding.

The idea is that a small, fast drafter guesses the next few tokens and the big model verifies them all in one pass. Accepted guesses are free. And critically, the technique is mathematically exact: rejected drafts are discarded, so the model emits precisely the tokens it would have emitted anyway. There is no quality tradeoff to weigh. It is the rare optimization that is simply better.

On our hardware it took stock vLLM from 32.8 to 85.6 tok/s. Same engine, same checkpoint, one config change.

Where the other 2× came from

Turning speculation on is the easy half. The surprise was how much the implementation of the verify step mattered.

A community fork of the exact same vLLM version — patched with split-KV verify attention, a 4-bit output head, and a reduced draft vocabulary — reached 167.8 tok/s where stock reached 85.6. Nearly 2× from patches that never touch the model.

The framework matters more than the drafter. We ran the identical DFlash2 drafter under two engines: 60.7 tok/s in llama.cpp, 212.1 in patched vLLM. People spend a lot of energy choosing drafters. The bigger win is in whose verify path you run it through.

Four things that lied to us

Every one of these produced numbers that looked completely reasonable. None raised an error. Together they cost more time than all the actual tuning.

1. The model was thinking, and we couldn't see it

Recent models emit reasoning tokens by default. If your server runs a reasoning parser, that text is extracted into a separate field — so a client expecting it inline receives an empty response, with HTTP 200 and a full token count.

One benchmark ran to completion, scoring a model whose output it literally could not read. Disabling it took our error count from 10 to 0 and halved the time per case. This bit us five separate times across four different harnesses, and client-side flags like --thinking off were repeatedly silent no-ops. What works is sending chat_template_kwargs: {"enable_thinking": false} and then checking the response is non-empty.

2. The second GPU was not idle

We ran two benchmarks on two cards at once, reasoning that separate GPUs are independent. They aren't — they share PCIe, host memory bandwidth and CPU, and batch-1 decode is latency-sensitive.

The same task measured 95.8 tok/s alone and 58.0 with the other card busy. A 39% error, invisible in the output. It invalidated a full day of context-scaling results, which now carry a correction banner in the log.

3. Our correction was also wrong

Having found the contention bug, we went looking for more of it — and "found" a 20% error in the headline table. It wasn't there. We had compared a 46-token prompt against runs at 1,100 tokens.

Speculative acceptance rises with context: a longer prefix of coherent text is easier to draft against. A clean control settles it — with speculation off, prompt length changes decode speed by 0.6%, which is to say not at all. Turn speculation on and the same engine gains 29–46% from prompt length alone.

The lesson we kept re-learning. Any speed comparison across different prompt lengths is meaningless unless you also report acceptance. Prompt length is a condition, like power cap or batch size — and comparing across it silently is exactly the mistake we'd just written a checker to prevent.

4. Generated code hung the harness for an hour

A correctness benchmark stalled. Not crashed — stalled, with a node process at 99.9% CPU for 68 minutes. The model had written JavaScript with an infinite loop, and the harness had no per-test timeout. If you run model-written code unattended, impose your own.

What long context actually costs

We expected decode speed to fall off a cliff as context grew. It doesn't — it declines gently, about 21% across a full 64K window. What falls off a cliff is the wait before the first token: +1.14 seconds per 1,000 tokens of prompt, with a correlation of 1.00. It is the most perfectly linear thing we measured.

At 61K context, a request waits 69 seconds before producing anything — roughly six times the entire decode time of the reply it then produces. For long-context work the speculator is close to irrelevant, and prefix caching is the only lever worth pulling.

A prediction we got wrong, in a useful direction. We expected draft acceptance to collapse as an agent's conversation history piled up — later turns being novel reasoning rather than reproduction. Across 68 turns of an agent building Tetris from scratch, context growing from 5K to 61K, acceptance stayed flat. We confirmed it with a second, unrelated agent harness. The slowdown at depth is attention cost over a growing cache, not speculation failing. That matters practically: the instinctive fix — reducing draft depth — does nothing at all.

Does any of it still work?

Speed is half a question. We ran the Aider polyglot benchmark — 225 real programming exercises across six languages, with a second attempt after seeing test failures.

Twenty-eight exercises were solved on the first try. Eighty-one more were solved only after the model saw its tests fail. The feedback loop is worth more than any serving configuration on this page. If you are building something agentic, wiring test output back to the model beats every optimization we spent five days finding.

Note what cannot move that number: because speculative decoding is exact, swapping drafters cannot change a correctness score. If you ever see one change, your harness is broken — which makes a useful self-test.

What we built so the next model takes a day

By the end we had a pile of scripts and a lot of hard-won knowledge about how to measure wrong. So we turned it into an instrument: six axes (speed, throughput, context, correctness, agentic behaviour, efficiency), one config file per model, and a fairness fingerprint — eleven conditions hashed into every result, with the comparison tool refusing to put two results side by side when they don't match.

That gate exists because of one number. When we deliberately ran a benchmark under wrong conditions, it reported 171 tok/s against the correct 144. Bad conditions look better. Nobody remembers three days later which flags a number came from, so the tool remembers instead.

Honest limits. One model, one machine, one architecture family, mostly at 4-bit. The fastest configuration is a third-party fork whose optimizations are checkpoint-specific — it refuses outright to load checkpoints quantized at a different group size. None of these figures are comparable to published leaderboard numbers: different quantization, harness versions, reasoning settings and serving stacks all move them independently. They are honest measurements of one deployment, not claims about what the model can do.
